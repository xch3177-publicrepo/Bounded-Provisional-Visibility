# W2D-E3 — Single-node ANN concurrency and throughput: preregistration

2026-07-29.  Written after the canonical W2D E1/E2 artifacts were accepted and
before any E3 runner, verifier, result, pilot, or E3-specific measurement code
exists.

## Question and scope

E1 and E2 establish the promotion-path accounting with a frozen real detector,
but E2 is Milvus Lite with an effective FLAT index and one formal replay.  E3
asks a narrower systems question:

> On one Milvus Standalone process, do the W2D retrieval and admission paths
> remain measurable under HNSW approximate search and concurrent query load,
> and what single-node throughput/tail-latency envelope is observed?

E3 is not a distributed-scaling experiment.  Milvus Standalone is a
single-machine deployment.  No E3 result may be described as scale-out,
distributed, production-scale, highly available, or fault tolerant.

E3 is also not a new detector-quality experiment.  It consumes the already
frozen D1 decisions and detector service times.  It neither re-scores a test
item nor enlarges the 512-source-group detector denominator.

## Deployment and independent run

The deployment is Milvus Standalone v2.4.15 over gRPC, with COSINE distance and
one HNSW index.  A formal run must record:

- server version and URI;
- effective index type, index state, and load state;
- Python, pymilvus, platform, CPU-count and memory descriptors;
- the Milvus process start metric from the port-9091 Prometheus endpoint;
- Git commit, tracked-tree status, and the E3 runtime fingerprint; and
- start/end UTC timestamps.

One independent run means:

1. Milvus Standalone was restarted after the preceding run;
2. its recorded process-start value differs from every earlier formal run;
3. the E3 collection is newly created and the HNSW index is rebuilt; and
4. the run writes one new, exclusively-created JSON file.

Five independent runs, numbered 1--5, are required.  Five workload seeds inside
one server process do not satisfy this requirement.  A missing or rejected run
is retained and is not silently replaced under the same run number.

## Static retrieval population

The formal population contains exactly 100,000 unique primary keys and
384-dimensional normalized float32 vectors:

1. all 1,752 frozen W2D embeddings, in frozen embedding-row order; then
2. 98,248 deterministic normalized Gaussian background vectors generated by
   NumPy `default_rng(7301)`.

The synthetic extension is a systems pressure load.  It is not called a real
text corpus and supplies no detector-quality or attack-generalization
denominator.  ANN accuracy is evaluated with all 192 frozen W2D query materials
from the protocol plan.  The exact reference is a NumPy COSINE top-5 over the
same 100,000-vector snapshot.

## Panel A: ANN fidelity and latency

The graph is built once with:

- `index_type = HNSW`;
- `M = 16`;
- `efConstruction = 200`; and
- consistency level `Strong`.

After flush, seal, index completion, and reload, the runner must verify that
HNSW is the effective serving index.  Against that one graph it runs
`ef = {20, 64, 256}`.  Rebuilding one graph per `ef` is forbidden because it
would confound the search parameter with graph construction.

One unreported warm-up pass precedes measurement.  Each of the 192 frozen
queries is then executed five times per `ef`; accuracy is computed once per
unique query and latency is reported over all 960 measured executions.  The
runner records, overall and by attack family:

- Recall@5 against exact FLAT ground truth;
- exact-top-5 match rate;
- top-5 landing concordance for the query-associated W2D item;
- query P50/P95/P99, maximum and count;
- query errors/timeouts; and
- insertion time, index-build time and effective index metadata.

`ef=64` is the primary operating point.  It supports transfer of the retrieval
observations only if its per-run Recall@5 is at least 0.95 in every accepted
run.  Failure is a result and does not authorize selecting `ef=256` after the
fact.  The other two points are a descriptive recall/latency sensitivity.

## Panel B: concurrent load

Panel B uses the same HNSW graph with `ef=64`.  The full matrix in each
independent run is:

- baselines `{B1, B2, B3, B4}`;
- closed-loop query concurrency `{1, 4, 8, 16}`;
- one fixed admission stream of 20 arrivals/s;
- a 5 s unreported warm-up and a 15 s measured window per cell;
- `T_p = 1.0 s`;
- verifier concurrency `4`; and
- top-k `5`.

Queries cycle through the 192 frozen W2D query vectors in a run-specific,
label-blind deterministic order.  Admissions cycle through the 512 frozen test
items in the frozen score order, allocate a fresh primary key on every replay,
and reuse the item's frozen embedding, D1 decision and one measured D1 service
time.  Repeated admissions are load events, not new detector observations.

The custom verifier returns the frozen decision immediately and replays its
measured service duration while holding a live verifier worker slot.  Queue
wait, queue depth, service time and commit latency therefore arise in the live
run.  This is a measured-service trace replay, not online detector computation,
and must be named that way.

The four policies use the shared `functional_slice.System` state machine:

- B1: immediate visible, no verification;
- B2: verify before visible;
- B3: immediate provisional visibility, asynchronous verification, no deadline;
- B4: immediate provisional visibility, independent one-second deadline.

The order of baselines uses the four rows of the frozen Williams square in runs
1--4.  Run 5 uses the first row again and is reported separately; it is not
claimed to improve position balance.  Concurrency order is rotated by run
number.  No cell or query is removed because of its outcome.

Each cell records:

- offered and achieved admission rate, dispatch lag and failed admissions;
- achieved query QPS, P50/P95/P99/max latency, errors and completed queries;
- verifier queue/service/commit summaries and cancelled/failed counts;
- the frozen detector-decision mix replayed in that cell;
- deadline, false-promotion, false-refusal and right-censoring counts derived
  from the live lifecycle;
- query-start and query-completion sentinel summaries before and after the
  cell; and
- cleanup confirmation and residual dynamic-row count.

The query requests are the observations for latency but not independent
experimental units.  The independent unit for a baseline/concurrency
comparison is one accepted server run.

## Environment and validity gates

The following gates are checked without reference to a favorable performance
direction:

1. Every frozen parent file has the preregistered SHA256.
2. The tracked tree is clean and all five results have the same Git commit and
   runtime fingerprint.
3. Deployment mode is `standalone`, server version is v2.4.15, and effective
   index type is HNSW in both panels.
4. The five process-start values are present and distinct.
5. The static population is exactly 100,000 unique ids and the measured query
   set is exactly the frozen 192-query set.
6. Panel A contains exactly three frozen `ef` points and 960 latency
   observations per point.
7. Panel B contains every one of the 16 baseline/concurrency cells in every
   run, with no substituted or dropped cell.
8. Every cell's offered admission count, completed/cancelled verifier count,
   query completion count, and error count balance.
9. B1 performs no verifier calls.  B2 admits nothing before a committed
   affirmative decision.  B3 has no deadline.  B4's deadline remains
   independent of the verifier queue.
10. Every cell cleans its dynamic id range and leaves no live task or timer.
11. The fixed sentinel workload's P95 movement across a cell is at most 1.5x.
    A larger movement rejects that run for protocol-performance attribution;
    its feasibility and raw measurements remain archived.
12. Strict JSON is mandatory: no NaN, Infinity, duplicate key or implicit
    undefined value.

Accuracy and performance outcomes do not invalidate their own run.  In
particular, Recall@5 below 0.95, achieved admissions below 95% of offered,
query error rate above 1%, a confidence interval crossing its null, or B4 being
slower than B1 are reportable negative outcomes, not reasons to rerun.

## Aggregation and stopping

The matrix stops at five accepted independent runs.  No sixth run is added
because a range is wide or a direction is unresolved.  A technical rerun is
allowed only for an explicit gate failure, uses a new attempt filename, and
does not delete the failed file.

Every per-run percentile is computed inside that run.  Across runs, E3 reports
the five run-level values, median, minimum and maximum.  It does not pool
requests across runs or call the resulting request count a sample size.
With five independent runs, intervals and directions are descriptive; no
formal population-level significance claim is made.

## Interpretation boundary

If all gates and the `ef=64` recall-transfer condition pass, E3 may support:

> In the tested single-node Milvus Standalone deployment, the frozen W2D
> decision/service trace was executable over a 100k-vector HNSW index under
> 1--16 concurrent query clients; the observed throughput, tail latency and
> ANN recall are reported over five independent process runs.

It may not support distributed scalability, horizontal speedup, production
capacity, high availability, fault tolerance, a 100k real-text corpus, online
detector CPU contention, a larger detector-quality denominator, robustness to
unknown attacks, or end-to-end RAG answer safety.
